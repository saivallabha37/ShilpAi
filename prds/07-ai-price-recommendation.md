# PRD 07 — AI Price Recommendation

**Project:** ShilpAI  
**SIH Problem Statement:** SIH26090  
**Module:** 07 — AI Price Recommendation  
**Status:** Final Draft v1.1  
**Scope:** MVP  
**Dependencies:** PRD 02, PRD 03, PRD 05  
**Downstream:** PRD 03 publishing flow, PRD 08 discovery

> **Important:** This module provides **price guidance**, not automatic price setting.

> Tags: `[CONFIRMED]`, `[PROPOSED]`, `[ASSUMPTION]`, `[OPEN]`

---

## 1. Objective

Help artisans estimate a transparent and explainable selling-price range from their own production information and configurable assumptions, while keeping the final price completely under artisan control.

## 2. Problem Being Solved

Artisans may know how to make a product but may not know how to translate material cost, labor time, and overhead into a consistent asking price. The system should provide decision support rather than silently deciding the price.

## 3. Scope

### In scope — MVP

- Material cost input.
- Labor-time input.
- Configurable labor/reference assumptions.
- Overhead input or configurable assumption.
- Transparent calculation.
- Suggested minimum/maximum range.
- Optional recommended point within that range.
- Confidence indicator.
- Explanation of calculation factors.
- Artisan selection/custom price.
- Non-blocking consistency warning.

### Out of scope — MVP

- Automatic price setting.
- Guaranteed fair wage.
- Guaranteed profitability.
- Live market-price scraping.
- Unverified government benchmark claims.
- Unverified craft-specific market ranges.
- Black-box pricing model.
- Dynamic ML pricing without a real dataset.

## 4. Target Users

**ARTISAN:** uses price guidance before publishing.

## 5. User Stories

- As an artisan, I want to understand how the suggested price was calculated.
- As an artisan, I want to enter my real material cost.
- As an artisan, I want to include my labor time.
- As an artisan, I want to choose a price myself.
- As an artisan, I want to ignore the recommendation if it does not fit my situation.
- As the system, I want numeric recommendations to come from deterministic calculations.

## 6. Functional Requirements

**FR-1** The system shall accept product and category context.

**FR-2** The system shall accept artisan-provided material cost when available.

**FR-3** The system shall accept artisan-provided production time/labor information when available.

**FR-4** The system shall support configurable overhead assumptions.

**FR-5** The system shall calculate a transparent cost basis.

**FR-6** The system shall produce a suggested range and optional recommended point.

**FR-7** Numeric outputs shall be generated by deterministic application logic.

**FR-8** An LLM, if used, may explain the already-calculated result but shall not independently determine the numeric price.

**FR-9** The artisan shall be able to:
- accept the recommended value;
- choose the minimum;
- choose the maximum;
- enter any custom price.

**FR-10** Custom prices outside the suggested range shall not be blocked.

**FR-11** The system shall store the final artisan-selected price separately from the recommendation.

**FR-12** The system may issue a non-blocking warning when the selected price appears inconsistent with the entered cost/labor assumptions.

## 7. Non-Functional Requirements

- **Transparency:** every numeric component must be inspectable.
- **Determinism:** same inputs + same configuration produce the same calculation.
- **Performance:** deterministic calculation should be near-instantaneous; exact target is `[OPEN]`.
- **Explainability:** the artisan can understand the recommendation without technical knowledge.
- **Safety:** recommendations must not be represented as guarantees.
- **Configurability:** reference assumptions should be changeable without changing business logic.

## 8. User Flow

1. Product/catalog data becomes available.
2. Artisan enters or confirms material cost.
3. Artisan enters or confirms labor/production time.
4. System loads configured assumptions.
5. Deterministic calculator computes:
   - material cost;
   - labor estimate;
   - overhead;
   - optional reference/heuristic component;
   - suggested range.
6. Confidence is assigned based on data completeness.
7. Optional LLM generates a human-readable explanation from the already-computed numbers.
8. Artisan reviews.
9. Artisan selects min/recommended/max or enters custom price.
10. System stores the final selected price.
11. PRD 03's publishing rules remain authoritative.

## 9. Inputs

| Input | Source | Required |
|---|---|---|
| Product ID | PRD 03 | Yes |
| Craft category | PRD 02 | Expected |
| Material cost | Artisan | Optional |
| Labor time | Artisan | Optional |

## 10. Outputs

Example:

```json
{
  "materialCost": 800,
  "laborEstimate": 1440,
  "overhead": 200,
  "referenceComponent": 0,
  "suggestedRange": {
    "min": 2400,
    "max": 3200
  },
  "recommendedPrice": 2800,
  "confidence": "medium",
  "finalSelectedPrice": null
}
```

The numbers above are an illustrative example only, not a government benchmark or craft-market claim.

## 11. Business Rules

1. This is price guidance, not automatic pricing.
2. Deterministic calculations are the source of numeric truth.
3. LLM output cannot introduce a new numeric price.
4. If reference data is unavailable, the system must use artisan inputs and transparent configured heuristics.
5. If critical inputs are missing, confidence should be reduced rather than fabricated.
6. Custom artisan price is always allowed.
7. Warnings are non-blocking.
8. The system does not guarantee statutory wage compliance.
9. The system does not guarantee profit or income.
10. The final artisan-selected price is distinct from the recommendation.
11. Price values must be stored with currency explicitly, with INR as MVP currency `[PROPOSED]`.

## 12. AI/ML Requirements

### 12.1 Numeric calculation

Use deterministic rules such as:

```text
baseCost = materialCost + laborEstimate + overhead

suggestedRange = transparent function(baseCost, configurable margin/heuristic)
```

The exact formula and configuration are `[OPEN]` and should be documented in implementation.

### 12.2 Optional LLM explanation

If used:

**Calculated numbers → explanation prompt → human-readable explanation**

The LLM must not be asked to “choose the price.”

### 12.3 Confidence

Suggested confidence interpretation:

- **High:** complete artisan inputs and stable configured assumptions.
- **Medium:** some configurable assumptions are used.
- **Low:** major inputs are missing or the result relies heavily on generic heuristics.

These labels are product guidance, not statistical confidence intervals.

### 12.4 External data

No claim about government census data, export council benchmarks, statutory rates, or craft price ranges may appear unless the actual source is documented, accessible to the implementation, and its scope/date is recorded.

## 13. API Requirements

The final price endpoint must respect PRD 03 authorization and state rules.

## 14. Data Requirements

Recommendation record should contain:

- product ID;
- material cost;
- labor time;
- labor estimate;
- overhead;
- reference/heuristic component;
- suggested min;
- suggested max;
- recommended value;
- confidence;
- calculation version/config version;
- explanation metadata;

`finalSelectedPrice` belongs to the product/pricing model defined by PRD 03; do not create a duplicate authoritative price field.

## 16. Security & Privacy

- Only the artisan may modify cost/labor inputs and final price.
- Buyers must never see private cost breakdown unless explicitly intended by a future product decision.
- Configuration values must be server-controlled.
- Prevent client-side manipulation of calculation results.
- Do not expose API credentials.
- Validate all numeric values for type, range, and currency.

## 17. Error Handling

| Scenario | Handling |
|---|---|
| Invalid cost | `400 VALIDATION_ERROR` |
| Negative labor time | `400 VALIDATION_ERROR` |
| Missing product | `404 PRODUCT_NOT_FOUND` |
| Unauthorized update | `403 FORBIDDEN` |
| Calculator failure | Return error; retain previous valid recommendation |
| LLM explanation failure | Keep numeric recommendation; explanation optional |
| Missing inputs | Lower confidence; request optional inputs |

## 18. Edge Cases

- Artisan enters zero material cost because materials were reused.
- Artisan does not know exact labor hours.
- Product takes several days with intermittent work.
- Custom price is below calculated cost.
- Custom price is far above the recommendation.
- Reference configuration changes after an earlier recommendation.
- Artisan changes material cost and recalculates.
- LLM explanation disagrees with numeric calculation.

In the last case, numeric calculation wins and the explanation must be discarded/regenerated.

## 19. Acceptance Criteria

- [ ] Recommendation is clearly presented as guidance.
- [ ] Numeric calculation is deterministic.
- [ ] LLM cannot independently set the price.
- [ ] No unsupported external market statistics are hard-coded.
- [ ] Material cost, labor, overhead, reference component, range, and final price are separated.
- [ ] Artisan can choose min/recommended/max.
- [ ] Artisan can enter any custom price.
- [ ] Custom price is never blocked solely for being outside the recommendation.
- [ ] Wage/cost inconsistency warning is non-blocking.
- [ ] Missing data lowers confidence rather than creating fake data.
- [ ] Final price follows PRD 03's product state machine.
